## Why I wrote this down

I kept shipping work that wasn't ready. Not visibly bad — subtly bad. Hierarchy that didn't earn itself. Components that looked like they used the design system but didn't. Screenshots that matched the intent but not the reality.

Every time, in the post-mortem, there was a moment I'd skipped. A gate I hadn't passed. A verification step I'd self-certified as "looks good" instead of running mechanically.

So I wrote the process down. Not as an aspiration — as a forcing function. Five gates. Each has to be passed before the next starts. Each has a mechanical output, not a vibe check.

The process is the same whether I'm building or whether Claude is building for me. That's the point — it's not a style guide, it's a cognitive architecture.

### Gate 1 — ORIENT

*What I read. What I understood. What I'm going to do.*

Before writing a line of code, produce a **Context Receipt**: every source document I read (not skimmed, not remembered from last session — actually opened), with one specific fact from each that proves comprehension.

This exists because Claude — and I — love to jump straight to building. The Context Receipt is an anti-skip mechanism. If it's blank, the build can't start.

### Gate 2 — THINK

*Hierarchy, emotional state, user context, patterns.*

Run the **Design Compiler** skill. Force first-principles ranking of every field on the screen. Each element has to earn its position. "This is how the prior design did it" is not a reason.

Run the **Emotional State** audit. What state does the user arrive in? What state should they leave in? If the screen doesn't know, it won't get there by accident.

### Gate 3 — BUILD

*Mobile-first. No unnecessary decisions. Patch mode by default.*

The default edit mode is **patch** — surgical changes via the Edit tool, not the Write tool. Rewrites require escalation because rewrites silently drop features. (I learned this the hard way: three critical feature systems went missing in one visual overhaul.)

Every modification gets a screenshot of the specific node that changed. Not a zoomed-out canvas view — the individual component. The screenshot has to appear in the conversation or the verification didn't happen.

### Gate 4 — CRITIQUE

*Mechanical audits, not vibe checks.*

This is the gate I skip most. It is also the most important gate.

<PullQuote>Self-certifying "looks polished" catches nothing. Scanning for <code>#fff</code>, counting uppercase, greppping focus-visible rules catches everything.</PullQuote>

The mechanical checklist runs every time:

- Zero pure black (`#000`) or pure white (`#fff`). All neutrals tinted.
- Zero uppercase labels (unless it's an acronym).
- Every interactive element has a `:focus-visible` rule.
- No bounce / elastic easing.
- Touch targets ≥ 44px.
- Reduced-motion media query present and honored.

Then the **adversarial relay**: Claude builds, ChatGPT critiques. If they disagree on whether something is ready, it isn't ready.

### Gate 5 — PRESENT

*With rationale and critique summary.*

The work is shown to the human reviewer with:

- What I changed (the diff).
- Why I changed it (reference back to the Context Receipt and hierarchy analysis).
- What the critic panel flagged and how I resolved it.
- What I'm *unsure* about, explicitly.

No "ta-da." No "done." Just the work and the rationale.

## Nineteen failure modes

The gates exist because I have nineteen documented ways of breaking them. A partial list:

1. Skipping Gates 1–2 and going straight to code.
2. Treating all UI elements equally (no hierarchy analysis).
3. Not reading existing project documentation.
4. Not invoking skills or agents.
5. Resisting external critique.
6. Rewriting entire files from memory instead of surgical edits.
7. Cargo-cult UI hierarchy — copying field order from prior designs without earning it.
8. Not running verification before presenting work.
9. Speed-running sessions to inflate a count. (Three deep sessions beat seven shallow ones.)
10. Building before installing quality tools.
11. Self-certifying visual quality without mechanical audit.
12. Building containers with plain frames instead of component instances.
13. Skipping post-build screenshot verification.
14. Resizing auto-layout parents before children.
15. Binding variables with value=0.
16. Not repositioning cloned variants.
17. "This is just a test" rationale for lowering the bar.
18. Batching all screenshots to "the end."
19. Assuming last session's state still applies this session.

The list grows. Every new failure mode that shows up gets logged and the gate that would have caught it gets a new mechanical check.

## What this is really about

The 5-Gate process isn't project management. It's **externalized metacognition**. I have ADHD. I get excited about building. I will absolutely skip Gate 4 if there isn't a forcing function that stops me.

The gates are that function. They don't make me a better designer in the moment. They make the *system* — me plus Claude plus ChatGPT plus the mechanical checklist — produce better work than any of us would alone.

Design process posts usually read like aspiration. This one is a ledger. Here are the ways I fail. Here are the checks that catch each one. Here is the artifact each check produces.

If you want the full process file — CLAUDE.md, the review checklist, the gate-by-gate artifacts — [it's on the tools page](/tools). Copy it, gut it, rebuild it around your own failure modes. The specific rules matter less than the pattern: **name your failures, name the check that catches each one, don't let the next gate start until the check has run**.
