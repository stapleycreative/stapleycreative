## The problem every AI build reveals

Hand Claude, Cursor, or Copilot a task in a real codebase and watch what happens.

It invents its own tokens. It produces colors close to — but not exactly — your palette. It writes a button that looks like your button but doesn't use your `Button` component. It respects half your typography scale and fabricates the other half.

The code looks "fine." It passes a cursory review. Merge it, and the design system drifts a little further away from itself. Do this for six months and you don't have a design system anymore — you have a design system's ghost, overwritten by whatever the AI defaulted to in each PR.

This is not a prompt problem. You can write "use the design system" in your `CLAUDE.md` and it doesn't help. The AI doesn't know what's in the design system. It's inferring from variable names, component names, and training data — all of which are fuzzier than your actual design rules.

**The AI needs ground truth, and no one has been giving it to them.**

## The insight: your Figma file already has the answer

Your Figma library already contains the tokens. Your design system already has rules ("use `--color-action-primary` for primary CTAs, never for destructive actions"). Your components already have recipes ("a Button requires these states, prohibits these variants, must meet these contrast ratios").

All of this is documented — scattered across Figma annotations, Notion pages, Slack threads. None of it makes it into the AI's context when the AI writes code.

So I'm building the bridge.

## What the plugin does

A Figma plugin reads your local variables, lets you author rules and component recipes directly in the plugin UI, and exports two files:

- A **markdown spec** — for pasting into `CLAUDE.md`, `.cursorrules`, Copilot instructions, or any AI context window.
- A **JSON spec** — W3C DTCG-inspired format with `$rules` extensions, for tooling.

That's it. One workflow. Figma variables → rules + recipes → exported spec file. No GitHub integration, no CSS export, no bidirectional sync, no linter. The v1 scope is deliberately small because **one workflow done well is worth more than five half-built.**

Four moving parts:

1. **Read tokens from Figma** — the plugin reads local variables, resolves aliases, builds a group tree, and handles Figma's 100KB-per-key storage limit by chunking rule data by collection.
2. **Let the designer author rules and recipes** — a React UI with four tabs: Tokens (browse + search), Rules (5 types: usage, dont-use, states, responsive, accessibility), Recipes (structured component specs), Export.
3. **Export structured spec files** — markdown for AI context, JSON for tooling. Both carry the same source of truth.
4. **Feed the spec into the AI** — paste into the project's AI instructions file, or point the AI's `file_search` at it.

## Three critics before any code

Before I wrote a line of code, I ran the concept through three independent reviewers:

- **ChatGPT (commercial viability)** — forced the scope from "design systems platform" down to "AI build reliability tool." Cut Tailwind export, GitHub integration, QA scanner. Introduced component recipes as the *real* unit of value — more useful to AI than isolated token rules.
- **Gemini (independent validation)** — 8.5/10 conviction. Added smart scaffolding (LLM-suggested rules the designer confirms), mode maps, and `$reasoning` fields that explain *why* a token exists.
- **ChatGPT, deep review of the brief** — cut MVP scope in half *again*. Flagged the Figma storage constraint before I hit it. Reframed positioning.

All three reviewers, working independently, pushed toward the same cut. That convergence was the signal to lock scope and start building.

This is the [adversarial critic relay](/blog/adversarial-critic-relay) in action — and the reason the plugin is being built with a scope guard instead of my normal urge to add "just one more feature."

## Why this matters beyond my own use case

Every design team with AI coding tools is losing ground to drift. The drift is invisible week to week. Over months, it's catastrophic.

The fix isn't "use the design system better in your prompts." The fix is giving the AI a **readable, structured, authoritative spec** it cannot miss. Then every PR either uses the spec or fails review for a concrete, cite-able reason.

This is the work I think design systems teams should be doing *now*. The first team to make their design system legible to AI tools doesn't just win the next year — they compound. Every AI-written PR in their codebase uses their system. Every AI-written PR in a system-free codebase drifts further.
